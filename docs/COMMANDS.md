# Command modules

Each of the 30 existing command handlers lives in its own file under `src/Server/Commands/`. For example, `GiveCommand.php` implements `executeGive`, and `TeleportCommand.php` implements the shared handler for `/tp` and `/teleport`.

`CommandRegistry` lists the supported names, aliases, handler methods and operator requirements. It supplies the same list for command advertisement, help and dispatch. A player-supplied name can select only a registered handler. `CommandArguments` handles tokenization; shared coordinate, player lookup and block-state helpers remain in the `Server/Commands.php` bridge.

Handlers are traits, following the server's existing trait-based organization. They are composed into the server so their private methods use the existing world/player services directly. No handler needs to expose those services publicly or bind closures into private state. `CommandDefinition` is an immutable registration record.

When adding a command:

1. Create its named handler file in `src/Server/Commands/` with an explicitly typed private execution method. Keep behavior specific to that command in that file.
2. Compose the handler into the bridge and add its name, aliases and permission requirement to `CommandRegistry`.
3. Put reusable parsing/services outside the individual handler. Keep arguments and local variables clearly named and format the whole file.
4. Add relevant behavior, permission, error and Java comparison coverage. An advertised command must execute its real behavior; accepting syntax alone is not implementation.

## Native feedback

`sendSuccess` and `sendFailure` in `Server/Commands.php` mirror `CommandSourceStack`. Feedback is a translatable component the client localizes. A success can be echoed to other online operators as a gray italic `chat.type.admin` message, and a failure is wrapped in red. Execution failures have no context line. The sender and join/leave messages use vanilla's player display name (click-to-message, insertion and entity hover, without team styling). `Nbt::component` writes compound fields in Java `HashMap` order, and `tests/text-component-unit.php` pins a join message byte-for-byte to an official capture. Older handlers still reply with plain English text, and the `sendCommandFeedback`/`logAdminCommands` gamerules are not modeled yet.

`/difficulty` and `/defaultgamemode` follow the official 26.3 bytecode: the same message keys, the "already set" failure, and difficulty broadcast to every player. As on a dedicated server, the values in `server.json` are reapplied at the next startup. `change_difficulty` reports an unlocked difficulty, matching vanilla captures; PHP previously sent it locked. `tests/difficulty-commands.py` checks exact component bytes, the operator echo, non-operator denial, a new player's default mode and the restart behavior. The official codecs decode its captures.

`/op`, `/deop` and `/kick` follow `OpCommand`, `DeOpCommands` and `KickCommand`. The op commands report the target's plain profile name, fail with `commands.op.failed`/`commands.deop.failed` when nothing changes, and persist the operator list to `server.json` at once. A player whose status changes receives vanilla's permission-level entity event (24 + level, 28 for operators) followed by a new command tree, the same pair sent on join. `/kick` disconnects each target with the rest of the input verbatim as the reason, or `multiplayer.disconnect.kicked`, then reports `commands.kick.success` with the display name and reason. Mixed plain and styled arguments use vanilla's wrapped list form (`{"": text}`). `selectPlayers` resolves names, UUIDs and the bare `@s`, `@p`, `@r` and `@a` selectors. Unknown profile names are not looked up on Mojang's service, so `/op` accepts any valid username. `tests/admin-commands.py` checks exact bytes for every message, permission event and disconnect; `tests/operator-persistence-unit.php` checks the file rewrite.

`/seed`, `/save-all`, `/save-on`, `/save-off` and `/stop` follow their 26.3 classes. `/seed` sends the seed as `ComponentUtils.copyOnClickText` (green, bracketed, click to copy) without an operator echo. `/save-all [flush]` reports `commands.save.saving` to the sender and echoes only `commands.save.success`. `/save-off` stops periodic saves, while block edits are still written as they happen (#7); shutdown always saves, as vanilla does. `/stop` echoes `commands.stop.stopping`, then shuts down gracefully, disconnecting players with `multiplayer.disconnect.server_shutdown` unless a deployment restart reason was left. Under Docker's `unless-stopped` policy the container then restarts. `tests/server-commands.py` checks every message and the shutdown.

`/list [uuids]` sends `commands.list.players` with the count and maximum as integer arguments and the players joined by `ComponentUtils.formatList` (display names, or `commands.list.nameAndId`, separated by a gray `, `), without an echo. `/weather clear|rain|thunder [duration]` reports `commands.weather.set.<type>` with an operator echo. There is no natural weather cycle yet, so the duration is validated but the weather persists until changed.

`/gamemode`, `/setworldspawn`, `/spawnpoint`, `/setblock` and `/fill` report vanilla's components with an operator echo. `/gamemode` accepts mode names only, is silent when a target's mode is unchanged, and tells another target `gameMode.changed` before reporting `success.other`. `/setworldspawn` and `/spawnpoint` take an optional yaw and pitch and report the block position, the float rotation and the dimension. The world spawn rotation is stored and sent in `set_default_spawn_position`, and `/spawnpoint` wraps the yaw, clamps the pitch, and respawns players at the block's bottom centre. Both remain Overworld-only, unlike vanilla, which records the dimension. `/setblock` and `/fill` fail with `commands.setblock.failed` and `commands.fill.failed` when nothing changes. `/fill` counts only changed blocks and reports `commands.fill.toobig` above the default 32,768-block limit. `/setblock` takes vanilla's `replace`, `keep`, `destroy` and `strict` modes. `/fill` takes `outline`, `hollow`, `destroy`, `keep`, `strict` and `replace <filter>`, where the filter is a block or block tag with optional properties. `destroy` sends the block-break event and drops the block's loot table without a tool (see [loot](LOOT.md)). Neighbour updates are not modelled either, so `strict` behaves like `replace`. Block positions must be in a chunk some player has loaded (`argument.pos.unloaded`) and inside the build height and world border (`argument.pos.outofworld`). `/tp` takes a rotation, `facing <location>` and `facing entity <target> [feet|eyes]`. A player then gets vanilla's `player_look_at` from their feet. Local `^` coordinates follow `LocalCoordinates` with `Mth`'s float sine table. `tests/world-commands.py` checks every message.

`/give`, `/summon`, `/kill` and `/tp` report vanilla's components with an operator echo. `/give` shows the item as `ItemStack.getDisplayName` (bracketed, colored by rarity, with a `show_item` hover) from `reference/26.3/display-names.json`, exported from the pinned JAR by `tools/ExportDisplayNames.java`, and fails with `commands.give.failed.toomanyitems` above a hundred maximum stacks. `/summon` reports the entity's display name with its UUID as insertion and hover, and summons at the sender's position when none is given. `/kill` sends `death.attack.genericKill` to every player, and to the victim's death screen, before reporting; an already dead player gets no second death message. Other death causes still use English text. `/tp` covers the location and entity forms for one or more targets: absolute X and Z without a decimal point are centred on the block, relative coordinates are resolved from the sender, and positions are reported with six decimals. A teleport confirmation for an earlier teleport is now ignored while a newer one is awaited, as in vanilla, instead of disconnecting the player. `tests/entity-commands.py` checks every message.

`/gamerule` accepts the 58 vanilla 26.3 rule names, with or without `minecraft:`, using their types, defaults and integer bounds from `reference/26.3/gamerules.json` (exported by `tools/ExportGameRules.java`). It reports `commands.gamerule.query` without an echo, `commands.gamerule.set` with one, and `commands.gamerule.not_set` for an unchanged value. `advance_time`, `keep_inventory`, `natural_health_regeneration`, `spawn_mobs`, `max_block_modifications` (the `/fill` limit), `block_drops`, `mob_drops` and `show_death_messages` have server behavior. So do `fall_damage`, `fire_damage`, `drowning_damage` and `freeze_damage` (as `Player.isInvulnerableTo` checks them) and `pvp`. `immediate_respawn`, `reduced_debug_info` and `limited_crafting` reach clients in the login packet and, when changed, as game or entity events. `send_command_feedback` silences successes and admin echoes, and `log_admin_commands` controls the console log of admin messages. The other rules are stored and reported but have no effect yet. Rules are kept in the Overworld and read once. Pre-26 camelCase names are unknown, as in vanilla. `/version` is operator-only on a dedicated server and sends vanilla's ten system messages (no echo or log) from the pinned JAR's version metadata in `reference/26.3/version.json`. `tests/rule-commands.py` checks both, including restart.

Damage uses vanilla's damage types from `reference/26.3/damage-types.json`, copied from the pinned JAR with their resolved tags. Death messages follow `CombatTracker.getDeathMessage`:
- `death.attack.<message_id>` names the victim, plus any direct attacker.
- Without a direct attacker, a player who hurt the victim in the last 100 ticks gets kill credit, giving the `.player` variant.
- A fatal fall of more than five blocks is `death.fell.accident.generic`.
- Creative and spectator players are invulnerable unless the type bypasses invulnerability. A hit within the invulnerability window lands only if it is stronger, and then only for the difference.
- `show_death_messages` hides the broadcast and empties the death screen's message.

Fall-location variants (ladders, vines, water) and weapon-name `.item` variants are not modelled yet. `/damage <target> <amount> [<damageType> [by <entity>]]` reports `commands.damage.success` or `commands.damage.invulnerable`, on players and mobs; its `at` and `from` forms are not supported yet. Void damage now starts 64 blocks below the world, as in vanilla. `tests/death-messages.py` checks every case.

`/time` follows 26.3's world clocks: the Overworld clock, which is PHP's day time, and the End's separate clock. Without `of <clock>`, it uses the sender's dimension's default clock; the Nether has none (`commands.time.no_default_clock`):
- **Forms:** `query time|gametime`, `set <time>|<marker>`, `add <time>`, `pause`, `resume`, `rate <rate>`, optionally through `of <clock>`.
- **Markers:** come from the `minecraft:day` timeline in `reference/26.3/timelines.json` (copied from the JAR by `update_reference.py`), and `set` moves forward to a marker's next occurrence.
- **Replies:** clock totals and game time are reported as Java longs. Queries are not echoed; changes are.
- **Ticking:** each clock ticks with vanilla's float partial tick and rate while `advance_time` is on and it isn't paused. Pause, rate and partial tick are saved with the world. A new world's clocks start at 0, as in vanilla (PHP previously started at noon); an existing world's End clock starts at its age.
- **Packets:** `set_time` follows vanilla. A join or dimension change sends every clock, a clock change sends that clock to everyone, and the periodic sync sends only the game time. The rate sent is the effective one.

Timeline queries and `time query daytime`'s parse error are not modelled yet. `tests/time-command.py` checks the replies, packets and restart.

The `commands` packet sends the official command graph for the vanilla commands implemented here, filtered to the player's permission level (4 for operators, vanilla's default op level, otherwise 0), so clients get vanilla's tab completion, argument types and suggestion providers. This server's own commands (`/spawn`, `/heal`, `/dimension`) keep a greedy string argument. `CommandTree` follows `Commands.fillUsableCommands` and `ClientboundCommandsPacket`:
- nodes shared by several parents are copied once
- redirects point at the copies
- nodes equal under `CommandNode.equals` (by command and argument type identity, ignoring redirects) share one entry, numbered breadth first
- flags include vanilla's restricted bit

The exporter records each node's real child order, argument type ID, suggestion provider, restricted flag and command and argument type identity. `tools/parity/command_tree.py` builds the complete operator and player trees and compares them with the official server's. Both have identical structure (2,399 and 26 nodes, 35,095 and 265 bytes). Only gamerule's children are in a different order: the official server lists them in hash order. `/help` prints brigadier's `getSmartUsage` of the tree the player was sent, one literal line per command, and `/help <command>` prints the usage below that node, as `HelpCommand` does. The parity tool compares both with the official server, and they match apart from gamerule's hash order. This server's own commands are executable on their own and take an optional string. `tests/command-tree.py` checks the trees actually sent and `/help`.

`command_suggestion` requests for the `ask_server` arguments in these commands are answered as `ServerCommandSuggestionsProvider` answers them: `/op` with online players who aren't operators, `/deop` with operators, and `/time set` with the clock's command time markers as full IDs. Matching uses `matchesSubStr` and `filterResources`, sorted case-insensitively. The parity tool checks these replies byte for byte. Other requests get an empty reply.

Entity arguments use `EntitySelector`, following `EntitySelectorParser` and `EntitySelector`:
- **Targets:** player names, UUIDs, and `@p`, `@a`, `@r`, `@s`, `@e` and `@n` with their default sorts and limits.
- **Options:** `type` (with `!`), `name`, `limit`, `sort`, `distance`, `x`/`y`/`z`, `dx`/`dy`/`dz` (box intersection), `gamemode`, `level`, `x_rotation`/`y_rotation`, and `tag` and `team` (nothing carries tags or teams yet).
- **Errors:** vanilla's for unknown, valueless, inapplicable or invalid options and empty results.
- **Not yet:** `nbt`, `scores`, `advancements` and `predicate` are rejected as unsupported, and selector syntax errors are plain messages without vanilla's context line.
- **Commands:**
  - `/kill` and `/tp` accept mobs in the sender's dimension: mobs die with their loot and no experience, or are moved and resynchronized
  - player-only arguments reject selectors that can match other entities (`argument.player.entities`)
  - single-target arguments reject `@a`-style selectors

Arguments are now separated by whitespace outside selector brackets and quotes. `tests/entity-selector-unit.php` checks parsing; the feedback recorder compares selector commands with the official server.

`tools/parity/command_feedback.py` runs one command script against PHP and the official server (with an accepted EULA) and compares every `system_chat` and `disconnect` payload byte for byte, for the operator and a non-operator witness. It also compares the scoreboard, team, title, status effect and world border packets that commands send, plus, for the commands that send them deliberately, sound (seeds zeroed), game event, entity event, damage event and attribute update packets. It covers `/list`, `/seed`, `/difficulty`, `/defaultgamemode`, `/save-all`, `/save-on`, `/save-off`, `/op`, `/deop`, `/kick`, `/weather`, `/gamemode`, `/setworldspawn`, `/spawnpoint`, `/setblock`, `/fill`, `/give`, `/summon`, `/tp`, `/kill`, `/version`, `/gamerule`, `/damage` with death messages, `/time`, entity selectors and parse errors, block modes, teleport rotation, facing and local coordinates, `/experience`, `/clear`, `/worldborder`, `/enchant`, `/ban`, `/pardon`, `/banlist`, `/whitelist`, `/tellraw`, `/title`, item components, `/scoreboard`, `/trigger`, `/team`, `/effect`, `/playsound`, `/stopsound`, `/rotate`, `/attribute` and `/summon` NBT, including their failures and echoes; all 1238 observations are identical. A `!respawn` line makes dead players respawn between deaths, a `!witness <command>` line runs the command as the non-operator, a `!quiet <command>` line runs a reset without comparing its reply, and a `!reconnect` line reconnects the witness. Random entity UUIDs in `/summon` replies, and the entity network IDs that effect, attribute, damage and entity event packets start with, are normalized before comparison, since each server numbers entities from its own counter. Attribute update entries are compared sorted, because vanilla orders them by identity hash. Players paired with a tracker again receive each other's attribute instances, and a killed mob's scores and team membership go once it is removed. Mobs dropped onto stone take vanilla fall damage, and mobs and survival players whose eyes are inside a suffocating block take `in_wall` damage while saturated healing runs. Score holders keep vanilla's `playerScores` hash order, including the table size earlier holders grew it to, and holders whose objective was removed stay listed until a reset empties them. `--commands FILE` runs another list of commands. The kick report and leave message are compared without order, because vanilla races them against the network thread. CI runs it in the command parity job.

Run `python3 tools/php_style.py` to format command modules and `python3 tools/php_style.py --check` to check them. Optional paths apply the same configuration to other changed PHP files. The helper verifies the pinned official PHP CS Fixer PHAR checksum and does not add a runtime dependency. CI checks command formatting.

`/experience` (alias `/xp`) adds, sets and queries points or levels with vanilla's messages. Setting points fails with `commands.experience.set.points.invalid` unless they fit within the current level. Players now keep vanilla's level, float progress and total separately (`Server\Experience`, a port of `Player.giveExperiencePoints` and `giveExperienceLevels`), including the level-up sound every fifth level. Saves that stored only a total are converted on load. `/clear` removes, or with a maximum of 0 counts, the matching items. It walks the hotbar, main inventory, armour, offhand, crafting grid and carried stack in vanilla's order. Its item predicate is an item, an item tag or `*`; component tests in the predicate are parsed but not compared yet.

`/worldborder` follows `WorldBorderCommand` on the sender's dimension. Each dimension's border (`World\WorldBorder`) is saved in its world and covers the centre, a size moving over game ticks, damage per block, the safe zone and the warning distance and time. Changes send vanilla's border packets to that dimension's players. A joining or respawning player gets `initialize_border` with any remaining lerp. Survival and adventure players outside the safe zone take `outside_border` damage, as in `LivingEntity.baseTick`. Mobs ignore the border, and nothing stops movement across it.

`/enchant` follows `EnchantCommand`. It enchants each target's main-hand item when the item is among the enchantment's supported items and compatible with its existing enchantments (`Enchantment.areCompatible` with exclusive sets), keeping the higher level. A single target reports `failed.itemless` or `failed.incompatible` with the plain English name, as `Component.getString` gives it on the server, from the pinned `en_us` names in `reference/26.3/en-us-names.json`. Several targets report only a total failure. The success names the enchantment in grey, or red for curses, with its level unless it has only one. Enchantment definitions come from `reference/26.3/enchantments.json`.

`/ban`, `/pardon`, `/banlist` and `/whitelist` keep vanilla's `banned-players.json` and `whitelist.json` beside `server.json`, and `whiteList` in `server.json` stands in for `server.properties`' `white-list`. As in `PlayerList.canPlayerLogin`, joining players are refused for a ban (`multiplayer.disconnect.banned.reason`, with the default or given reason), then when the whitelist is on and they are neither listed nor operators (`not_whitelisted`), then when the server is full (`server_full`). A banned online player is kicked with `multiplayer.disconnect.banned`. A login that replaces an online session kicks the older one with `duplicate_login`. `/banlist` and `/whitelist list` follow vanilla's `HashMap` order. Players are resolved as `GameProfileArgument` resolves them: online players, or for offline names an offline-mode UUID. An online-mode server stores the name without a Mojang profile lookup. IP bans are not supported, and the whitelist is not enforced on players already online, matching `enforce-whitelist=false`. `tests/player-lists.py` checks the kicks, rejections, operator bypass and reloading.

`/tellraw` and `/title` take vanilla's text component argument: an SNBT value (`Commands\Snbt`, after `TagParser`) decoded as `ComponentSerialization.CODEC` does (`TextComponentArgument`). The value can be a string, a list whose first entry carries the rest as siblings, or a compound with one content type, style fields, events and extra. Malformed values fail with `argument.component.invalid`, quoting DataFixerUpper's message for the common cases. Before sending, components are resolved as `ComponentUtils.updateForEntity` resolves them: selectors become the matching names joined by their separator (grey ", " by default), and scores and NBT become empty text, since there are no scoreboards yet. `/title` sends the title, subtitle, action bar, animation times and clear/reset packets, and reports `commands.title.*.single|multiple`.

Item arguments take component patches (`ItemArgument`, after `ItemParser`). `damage`, `enchantments` and `stored_enchantments` are validated as their codecs validate them, with vanilla's `arguments.item.component.malformed` messages, and stored on the stack. So is `!component` removal, and so is the damageable-and-stackable check. Other components are shown in the reply but not stored yet. The `/give` reply hovers the item with its patch, and enchanted items take the raised rarity colour (`ItemStack.getRarity`). `/clear` item predicates compare damage and enchantments exactly.

`/scoreboard` follows `ScoreboardCommand` for objectives (`list`, `add`, `remove`, `modify displayname|rendertype|displayautoupdate`, `setdisplay`) and players (`list`, `get`, `set`, `add`, `remove`, `reset`, `enable`, `operation`). Number formats are not supported yet. The scoreboard (`World\Scoreboard`) is saved with the Overworld. Objectives iterate in fastutil `Object2ObjectOpenHashMap` order and score holders in `HashMap` order, as the list replies and `*` expose. As in `ServerScoreboard`, only displayed objectives are synchronized. Showing one starts tracking it (objective, slots and scores), hiding it stops tracking, a score is sent when created or changed, and a holder left without scores is reset for everyone. Joining players get the tracked objectives. Deaths count for `deathCount` objectives, and a killer earns `totalKillCount` and `playerKillCount`. `/trigger`, available to every player, adds 1 to (or `add`s to or `set`s) the player's own enabled trigger score and locks it again. Score components resolve to the score's value, and selectors accept `scores={objective=range}`. The other automatic criteria are not modelled yet (#26).

`/summon` reads the NBT compound with `Commands\Snbt` and applies the tags this server keeps: `CustomName`, `CustomNameVisible`, `NoAI`, `Silent`, `Invulnerable`, `PersistenceRequired`, `Tags`, `Health`, `Rotation`, and `Age` (negative for a baby). The custom name, its visibility, silence, the no-AI flag and the baby flag reach clients as entity data. A named mob's display name is its custom name, in the reply and in kill and death messages. Non-summonable types such as the player fail with `entity.not_summonable`. Selectors match `name=` against the custom name, or the English type name ("Pig"), as `Entity.getName().getString()` does, and match `tag=` against the mob's tags. `@e` and UUIDs also select dropped item entities, which `/kill` removes and `/tp` moves. A mob more than 64 blocks below the world is discarded, as in `Entity.checkBelowWorld`. A NoAI mob does not move or fall. Other NBT tags are accepted but not applied.

`/team` follows `TeamCommand` (`list`, `add`, `remove`, `empty`, `join`, `leave`, `modify`) with vanilla's replies. Teams live in the scoreboard, in fastutil order, and members in `HashSet` order. `set_player_team` packets carry vanilla's 26.3 layout: names, visibility and collision ids, an optional colour and the option bits. A new team is reported under its name, then its display name as a change. Joining players get every team with its members. Player display names everywhere are formatted for their team, as `PlayerTeam.formatNameForTeam` formats them: prefix, name and suffix in the team colour. Selectors match `team=`. Death messages follow the team's `deathMessageVisibility`, and team mates without friendly fire cannot hurt each other. `nametagVisibility` and `collisionRule` reach clients; server-side collision rules are not applied yet.

`/effect give|clear` follows `EffectCommands`. Players carry status effects (`Server\Effects`, with definitions exported by `tools/ExportMobEffects.java` to `reference/26.3/mob-effects.json`). Effects follow `MobEffectInstance.update`: a stronger effect replaces the current one, an equal one only lengthens it, and a change in visibility counts. Their packets match vanilla's: a new effect blends in and an updated one does not; hiding particles hides the icon; the remaining time is resent every 30 seconds; and a joining player gets saved effects without blending. Attribute modifiers on synchronized attributes reach the client (speed, slowness, haste, jump boost, health boost and the like). Regeneration, poison (never below 1 health), wither, hunger, instant health and damage, and saturation tick as vanilla's effects do. Resistance and fire resistance reduce damage. Strength and weakness change melee damage. Effects are saved with the player and end at death. Absorption grants its hearts (`AbsorptionMobEffect`), which take damage first and are cleared with the effect. Health boost raises the maximum health, and its removal clamps health back. Eating applies the food's consume effects from the official `consumable` components (`reference/26.3/consumables.json`, exported by `tools/ExportConsumables.java`): apply effects with their probability, remove effects and clear all effects. So golden apples give regeneration and absorption, and rotten flesh may give hunger. Foods with `canAlwaysEat` are eaten at full hunger, and each takes its `consume_seconds`. Random teleporting (chorus fruit), drinking potions and effects on mobs are not modelled yet. `tests/effects.py` checks eating, absorption damage, health boost, saving and death.

`/attribute` follows `AttributeCommand` for players and mobs: `get`, `base get|set|reset` and `modifier add|remove|value get`, with vanilla's replies and failures (an entity type without the attribute, a missing or duplicate modifier, non-living targets). Attribute definitions (protocol id, default, range and whether clients see them) come from `reference/26.3/attributes.json`, exported by `tools/ExportAttributes.java`. Values follow `AttributeInstance.calculateValue`: added amounts, then multiplied base, then multiplied total, clamped to the attribute's range. Modifiers keep insertion order, and status effects share them, removing and re-adding their own. Changed synchronized attributes reach the entity and everyone tracking it after the reply. A player's base values and command modifiers are saved and survive death, while effect modifiers do not. The maximum health reads `max_health`, so lowering it clamps health. Mob AI does not read attributes yet.

`/playsound` follows `PlaySoundCommand`. Each target in range hears the sound as a direct sound event, by name, as vanilla sends it. A target out of range hears it two blocks away at the minimum volume, or not at all without one. `/stopsound` sends vanilla's `stop_sound` flags for a source (`*` for any) and an optional sound.

`/rotate` follows `RotateCommand`. An absolute rotation is sent as is, unclamped. A `~` rotation is relative to the command source's rotation and is sent as the change from the target's, which the client adds. `facing` sends `player_look_at` as `/tp facing` does. Players' eye height is the float `1.62f`.

## Parsing

Before a handler runs, `CommandTree::parse` repeats Brigadier's `CommandDispatcher.parse` over the player's command tree. It tries every relevant child on its own `StringReader`, follows redirects, and prefers the branch that consumed the input. `Commands.getParseException` and `finishParsing` then choose the error. `ArgumentReader` ports the readers for the argument types these commands use: numbers with bounds, booleans, strings, entity selectors and names, game profiles, messages, game modes, anchors, times, identifiers, registry resources, block positions, vectors and rotations. Item, block and block-predicate ids are checked against the registries. Their components, properties and NBT are consumed as one balanced token and not validated. A parse error is sent as vanilla does: the red message, then a gray line with up to ten characters before the cursor, the rest underlined in red, and `<--[HERE]`, which suggests the command on click. `tests/command-parse-unit.php` pins keys and cursors recorded from the official server. Handlers still read their arguments from the whitespace tokens, and execution contexts (`/execute`) and result semantics remain in #10. Console/RCON command sources remain in #14. The full command inventory must come from the pinned Java 26.3 dispatcher.

The [native command inventory](command-coverage.md) tracks all 92 official roots/aliases and both default/all-feature argument graphs. Existing handlers are marked partial; registration does not establish native command behavior. Regenerate the matrix with `python3 tools/command_coverage.py` and check it with `--check`.
